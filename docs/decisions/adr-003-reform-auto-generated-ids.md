# ADR-003: 自動生成IDの生成規則依存を廃止し、ランダムID方式に移行する

## ステータス

Accepted

実装計画: [Plan](../plans/plan-reform-auto-generated-ids.md)

## コンテキスト

### 現状の自動生成ID

SKAM プロジェクトでは、3種類のエンティティにIDが自動生成される:

| 種類     | 形式      | 生成場所                                                          | 生成ロジック                                           |
| -------- | --------- | ----------------------------------------------------------------- | ------------------------------------------------------ |
| Token ID | `t{連番}` | `parser-core.ts:243`                                              | `++state.tokenIndex`                                   |
| Mark ID  | `m{連番}` | `parser-core.ts:247` (パーサー), `operations/index.ts:203` (CRUD) | パーサー: `marks.length+1`, CRUD: 既存IDの最大値+1     |
| Block ID | `b{連番}` | `parser-core.ts:954`                                              | `++state.blockIndex` (xml:id がなければフォールバック) |

### 問題点

#### 1. 生成規則に依存した判定

`parser-core.ts:623` で、highlight-ref の対応関係解決時に:

```typescript
const hasExplicitId = singleRef.id && !singleRef.id.startsWith('m');
```

IDが `m` で始まるかどうかで「自動生成かユーザー指定か」を判定している。ユーザーが `my-ref` のようなIDを指定すれば正しく動作するが、`m1-note` のように `m` 始まりのIDを指定すると自動生成扱いされてエラーになる。

#### 2. 2つの生成ロジックの不一致

- **パーサー**: `marks.length + 1` ベース — marks配列の現在の長さに1を足す
- **Operations**: `max(既存IDの数値部分) + 1` — 正規表現で `m{数値}` パターンを探索

同一ドキュメントに対して異なるIDが生成される可能性がある。

#### 3. ユーザーIDとの干渉

`operations/index.ts` の `generateId` は `m{数値}` 形式のIDのみを認識して連番管理する。ユーザーが `m100` を手動で設定すると、次の自動生成が `m101` に飛ぶ。

### 検討した選択肢

| 選択肢               | 概要                            | 長所         | 短所                             |
| -------------------- | ------------------------------- | ------------ | -------------------------------- |
| **A. State追跡のみ** | パーサー内で `Set<string>` 追跡 | 変更最小     | operations の形式依存が残る      |
| **B. ランダムID**    | UUID/nanoid                     | 衝突不可能   | 人間可読性低下                   |
| **C. メタデータ型**  | ID をオブジェクト化             | 型レベル保証 | SKAMDocument型変更が必要、影響大 |
| **D. 折衷案**        | 人間可読ランダム + State追跡    | バランス良好 | テスト更新が必要                 |

## 決定

**選択肢D: 人間可読ランダムID + State追跡** を採用する。

### 新しいID形式

`{prefix}-{8 hex chars}` (例: `t-a7f3b2c1`, `m-5e2d1a9b`, `b-c3f4e6d8`)

- 人間がIDの種類を即座に識別可能（prefix部分）
- ランダム部分（8 hex = 4バイト、約43億通り）でユーザーIDとの衝突を回避
- ハイフン `-` で区切ることで、既存の `m1`, `t1` 形式と明確に区別

### 自動/手動の判定方法

パーサー内で `autoGeneratedIds: Set<string>` を保持し、自動生成したIDを記録する。判定時は文字列形式ではなくSet照合で行う。

### ID生成のinjectable化

パーサーの `ParseOptions` に `idGenerator?: IdGenerator` を追加し、ID生成戦略を外部から注入可能にする。

- **本番**: `createRandomIdGenerator()` (デフォルト)
- **テスト**: `createSequentialIdGenerator()` を注入して既存のテストアサーションを維持

### `generateId` API の変更

`delimiter` パラメータを削除し、ランダム生成に変更する。

```typescript
// Before
export function generateId(doc: SKAMDocument, prefix = 'm', delimiter = ''): string;
// After
export function generateId(doc: SKAMDocument, prefix = 'm'): string;
```

## 影響

### 公開API変更（breaking change）

- `generateId` の `delimiter` パラメータ削除
- `ParseOptions` に `idGenerator` フィールド追加（後方互換、optional）

### 影響を受けるパッケージ

| パッケージ                | 変更内容                                                      |
| ------------------------- | ------------------------------------------------------------- |
| `@kanbun/skam`            | `IdGenerator` 型追加、`generateId` API変更                    |
| `@kanbun/skam-xml-parser` | `ParseOptions` 拡張、`ParserState` 変更、`hasExplicitId` 修正 |
| `@kanbun/playground`      | `generateId` 呼び出し修正（1箇所）                            |

### 影響を受けないパッケージ

- `@kanbun/skam-html-renderer` — IDは不透明な文字列として扱っている
- `@kanbun/skam-xml-stringify` — IDをそのまま出力している

### テスト影響

- `generate-id.test.ts`: 全面書き直し
- `crud.test.ts`: 自動生成ID部分のアサーション変更（~15箇所）
- `scenarios.test.ts`: 自動生成ID部分のアサーション変更（~3箇所）
- `comprehensive-marks.test.ts`: addMark経由のID部分（~3箇所）
- `parser.test.ts`: sequential generator注入で対応（~4箇所）
- fixture IDのみ使用するテスト（queries, display, type-guards, roundtrip, stringify, renderer系）は変更不要
