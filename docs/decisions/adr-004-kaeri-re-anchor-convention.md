# ADR-004: レ点のアンカートークン慣例変更（上→下）

## ステータス

Proposed

## コンテキスト

### 問題

SKAM データモデルにおいて、レ点（`type: 'kaeri', value: 'レ'`）が隣接2トークンのペアのうち**上のトークン**（原文順で先）にアンカーされている箇所がある。

例：「學而時習之」でペア (習, 之) を入れ替える場合

```json
// 現行（一部テスト/フィクスチャ）
{ "type": "kaeri", "anchor": { "from": "t4"(習), "to": "t4"(習) }, "value": "レ" }
```

### 背景

漢文のレ点は「下の文字を先に読み、上の文字に戻る」ことを指示する返り点。伝統的な書写慣例では、レ点は**下の文字**（原文順で後、先に読むべき方）の横に配置される。

### 現状の不整合

| ソース                         | レ点アンカー位置       | 例       |
| ------------------------------ | ---------------------- | -------- |
| SKAM仕様 JSON (Appendix A)     | 下のトークン (t5=之)   | ✓ 正しい |
| SKAM-ML 仕様 Section 11.1      | 下のトークン (之の後)  | ✓ 正しい |
| SKAM-ML 仕様 Section 7.2       | 上のトークン (而の後)  | ✗ 不整合 |
| XML fixture kaeri-basic.xml    | 上のトークン (而の後)  | ✗ 不整合 |
| XML fixture readme-example.xml | 時の後（ペアに無関係） | ✗ バグ   |
| multiple-blocks.xml            | 下のトークン (之の後)  | ✓ 正しい |

仕様書内とフィクスチャ間で慣例が揺れている。

### レ点以外の返り点について

今回のスコープは `value: 'レ'` のみ。一二点・上下点等は別途検討。

なお、仕様 JSON (Appendix D) の複合返り点例では:

- `value: '二'` on t2(可) = 下のトークン ← 一貫
- `value: '一レ'` on t4(學) = 下のトークン ← 一貫

複合返り点（一レ、二レ等）は今回変更しないが、将来的に同様の「下のトークン」慣例に統一する候補。

## 決定

### レ点は下のトークンにアンカーする

ペア (A=上, B=下) でレ点により B→A の順に読む場合、レ点マークのアンカーを B（下のトークン）に設定する。

```json
// 変更後
{ "type": "kaeri", "anchor": { "from": "t5"(之), "to": "t5"(之) }, "value": "レ" }
```

### コード変更は不要

- **XMLパーサー**: `precedingTokenId` ロジック維持。XML上で `<skam:kaeri kind="re"/>` を下のトークンの後に配置すれば正しいアンカーが得られる
- **stringify**: `mark.anchor.from` のトークン直後にkaeri要素を出力。アンカーが下のトークンなら出力位置も自動的に正しい
- **レンダラー**: アンカートークンの suffix-row にkaeriten 描画。下のトークンへの移動は伝統的配置に合致

### 変更対象はデータのみ

- SKAM-ML 仕様書の例文
- SKAM-ML 正規化ルールの注記
- XML テストフィクスチャ
- テスト期待値（パーサー、stringify、roundtrip）

## 影響

### positive

- 伝統的漢文書写慣例との一致
- 仕様書JSON (Appendix A) との一致
- レンダリング位置が伝統的配置（下の文字の横）に改善

### negative

- 複合返り点（一レ等）との一時的な不整合（将来課題）
- 大量のテスト期待値更新が必要

### 今後の課題

1. 複合返り点（一レ、二レ等）の同様の慣例変更検討
2. SKAM-ML の原文順 vs 訓読順 XML の明確な仕様化
