# ADR-047: SKAM-ML を妥当な SKAM JSON の完全な書き方にする

## コンテキスト

backlog の項目「範囲の重なりと部分的な交差は、JSON では表現できるが、XML では `unsupported` になる」から始めた。利用者の目的は、XML で記述した状態を集積して再利用することで、再利用にはほかの文書から字・ブロック・注記を指すことが入る。

当時の SKAM-ML は、validator を通る JSON の一部しか書けなかった。

- 重なる注記、2 書記素以上の字、空白だけの字、`custom`、文書・ブロック・字の `ext`、`placementHint` は、XML に書くと損失として落ちた (ADR-028、ADR-040、ADR-042)。
- 字と多くの注記の id は、XML を読むたびに乱数で振り直された (ADR-003)。
- 読みと部分交差した注記は、描画で範囲が変わるか、字が消えた。

## 利用者の決定 (2026-10-21〜22)

1. 範囲は XML を完全にする。再利用には、ほかの文書から箇所を指すことが入る。
2. 基本は入れ子で書ける前提で進める。部分交差だけを、本文の中の始まりと終わりの空要素の対で書く。
3. 手書きの id と自動の id の体系を分ける。手書きの id は固定、自動の id はブロックの中の位置で決まる。
4. highlight と ref は名指し (`ref` 属性) だけで結ぶ。1 つのラベルを離れた複数の傍線で共有し、傍線の中に傍線と関係のない ref (注の番号など) が入るため。
5. derivations は今のまま XML に書かない。
6. エディタはセットで提供する前提とする。エディタは JSON を編集し、保存のときに stringify で XML を書く。手で書いた XML のコメントと改行は残さない。
7. 「`<yomigana>x<saidoku>y</saidoku></yomigana>` は XML の時点でやってはいけない」。再読文字と読みの重なりは警告にする。
8. 登録簿に無い拡張は、`uri` を省いて宣言する。
9. 同じ種類の読みが 1 字でも重なる形は、矛盾として警告にする。
10. VRT の基準画像の補正の漏れは、描画の PR で直す。
11. 同じ字を共有する傍線は、外側にずらして並べる。

## 決定

### 「同じ文書」と往復の保証

validator が誤りも下の警告も返さない文書 d について、`stringify(d)` は損失を報告せず、`parse(stringify(d))` は d と同じ文書になり、`stringify(parse(stringify(d)))` は `stringify(d)` と同じ文字列になる。「同じ文書」は次で定める。

- derivations を除く。
- `extensions` と `extensionsRequired` は名前の集まりとして同じ。
- blocks と各ブロックの tokenIds は順まで同じ。tokens は id ごとに text、ext、custom が同じ。
- ブロックと字の id は値まで同じ。
- marks は、種類・anchor / position・値・属性・ext・custom・placementHint が同じ注記が同じ数ある。同じ anchor (または position) で同じ種類の注記どうしの相対の順は保つ。注記の手書きの id は値まで同じで、注記の自動の id は値が変わってよい。
- ext と custom の値は JSON の値として等しい。

損失の検出は、validator を通らない JSON と警告のある JSON のために残す。

### id の体系

- 手書きの id は XML の NCName。自動の id はブロックが `b#<順>`、字が `<ブロックの id>#<順>` で、XML には書かない。parser が位置から計算する。注記の自動の id は `m#<正の整数>` で、parser が手書きの id の無い注記に文書の順で付ける。自動の id は安定を約束しない。外から指す箇所には手書きの id を付ける。
- 手書きの id は、`<skam:t>` とすべての注記の要素に `xml:id` で書ける。
- 同じ anchor の yomigana・okurigana・soegana は 1 つの `<skam:kun>` に書くので、手書きの id を持てるのは最初の 1 つだけ。
- core が判定、計算、付け直しを持つ (`renumberAutoIds`、`convertHandIdsToAuto(doc, keep)`)。parser の `idGenerator` の引数は消した。`generateMarkId` は使われていない最小の `m#<n>` を返す。
- 文書をまたいで指す形 (文書の識別子と id の組) は決めない。

### `<skam:t>`

字を 1 つ表す要素。内容は文字だけで、書記素に分けず空白も捨てない。stringify は、平文で書くと parser の分け方 (ADR-042) で同じ字の並びに戻らない字と、手書きの id・ext・custom を持つ字を `<skam:t>` で書く。本文の CR と属性値の U+0009・U+000A・U+000D は文字参照で書く。

### ext / custom / placementHint

- 書き方の定義のある拡張の値は、拡張の名前空間の属性で書く (ADR-040)。それ以外の ext の値は持ち主の要素の `skam:ext` 属性に、custom は `skam:custom` 属性に、どちらも JSON で書く。placementHint は `placement-hint` 属性に書く。
- parser は属性の JSON を、長さの上限 (1,000,000 文字) と自由なデータの検査に通す。
- 登録簿にも定義にも無い拡張は、`skam:extension` の `uri` を省いて宣言する。parser は `uri` の無い宣言を名前で照合する。

### 内容モデルと空要素の対

- §7.0 の内容モデルを緩めた。テキストを持てる要素は、テキスト、`<skam:t>`、すべての注記の要素、位置の注記、空要素の対を子に持てる。ただし `skam:yomigana` と `skam:kun` は `skam:saidoku` を子に持てない。内容モデルの表 (`SKAM_ML_CONTENT_MODEL`) は core に置き、parser と stringify が使う。
- 入れ子にできない範囲だけを `sID` / `eID` の空要素の対で書く。注記の属性は始まりの要素に書く。
- stringify の選び方は次のとおり。範囲を (始まりの昇順、終わりの降順、§7.0 の入れ子の順、注記の順) で並べ、開いている入れ子の範囲のスタックと比べる。包含か離れていれば入れ子、そうでなければ対にする。同じ anchor の同じ種類の注記は、全部入れ子か全部対にする。混ぜると、読み直したときに注記の順が入れ替わるため。
- 字と字の間の出力の順は、閉じるタグ、終わりの空要素、位置の注記、始まりの空要素、開くタグ。
- 範囲の要素の深さの上限は 56 (`SKAM_ML_MAX_RANGE_DEPTH`)。parser は超えたら誤りにし、stringify は超える範囲を対にする。

### 検証の警告

どれも 0.3 では警告 (`valid: true` のまま) で、0.4.0 で同じコードの誤りにする。

- `ID_FORM`: NCName でも位置に合う自動の形でもない id、SKAM-ML に書けない ref を指す `highlight.ref`、同じ anchor の読みの 2 つ目以降の手書きの id。
- `XML_UNWRITABLE_CHAR`: XML 1.0 で書けない文字。
- `SAIDOKU_READING_OVERLAP`: yomigana か okurigana の範囲が再読文字の字を含む。
- `SAIDOKU_MULTI_TOKEN`: 2 字以上の再読文字。SKAM-draft §6.7 の「1 つの文字を複数回読む」に合わない。2 字以上の再読文字が別の範囲と部分交差すると対の書き方の特例が要り、意味の無い形のために記法を増やすことになるので、損失にとどめず誤りに向かわせる。
- `READING_OVERLAP`: 同じ種類の読みが別の anchor で 1 字でも共有する。SKAM の読みは字の横の 1 つの置き場で、側を区別する属性を持たない。

lint には `HIGHLIGHT_REF_UNLINKED` を足した。`ref` 属性で結ばない highlight の範囲に ref がちょうど 1 つあるときに知らせる。名指しだけで結ぶので、`ref` 属性を書かずに中の ref で結んでいた XML は結ばれなくなるため。

format は `skam@0.1` のまま上げない。古い parser は format を見て誤りにするだけで、新しい形を読めるようにはならない。0.3 で書いた SKAM-ML は 0.3 以上の parser で読む。

### 描画

- AIR は、範囲の読みを `ruby-group` にし、字ごとの要素を 1 回だけ持つ。各字の注記と位置の注記はその字の slot に付く (`joinedWithNext`、`saidoku`、`emphasisStyle`、`kutotenValues`、`refLabels`)。
- 竪点と傍線は、交差する範囲で断片 (`continuesBefore` / `continuesAfter`) に分ける。`getTatetenGroups` / `getHighlightGroups` は字ごとにすべてのグループを返す。
- 同じ字を共有する傍線は、段 (`lane`) を分けて外側へずらす。
- `READING_OVERLAP` の文書では、`marks` で先の読みを描き、それと字を共有する後の読みは描かない。同じ字の 2 つ目以降の傍点は描かない。
- 描画の上限は、1 ブロックの竪点と傍線 1,024 個、1 つの注記の断片 8 個、範囲の深さ 56 とした。validator を通らない文書でも描画の手間が爆発しないためで、上限を超えた注記は描かず、字は必ず描く。

## 却下した案

- **重なる範囲だけを本文の外の `<skam:marks>` 節に字の位置で書く (差分最小)**: 往復で失わないのは重なりだけで、ほかの損失と id の振り直しが残る。字の位置で指すので、手で本文を直すと範囲が黙ってずれる。
- **XML も JSON と同じ stand-off にする (白紙設計)**: 変換は 1 対 1 になるが、本文が字ごとの要素になって人が読めず、今の SKAM-ML と別の方言になる。
- **再読文字を空要素の対で書く特例**: 始まりの要素に読みの形を持たせる記法が要る。対にしなければならないのは 2 字以上の再読文字だけで、その形は意味を持たない。
- **注記を 1 つずつ入れ子か対に決める**: 同じ字の同じ種類の注記で入れ子と対が混ざると、読み直したときに注記の順が入れ替わる。
- **同じ字の 2 つの読みの置き方を選ばせる**: 読みは字の横の 1 つの置き場で、どちらの置き方にも正解が無い。矛盾として警告にした。
- **字が複数の範囲に属せる一般の形**: 同じ種類の読みが重ならないなら、字から読みへの対応は 1 つで足りる。竪点と傍線だけを、字からの複数の対応にした。
- **重なる傍線を警告にする**: 同じ字を共有する傍線は、利用者の文書の普通の形。段を分けて描く。

## 結果

- PR #70 (95cb6c5): id の体系、lint の `HIGHLIGHT_REF_UNLINKED`、`ID_FORM`、`XML_UNWRITABLE_CHAR`。
- PR #71 (2cd9370): `<skam:t>`、ext / custom / placementHint の属性、属性値の文字参照。
- PR #72 (c34e924): 緩めた内容モデルと空要素の対、`uri` を省いた宣言、再読文字の警告 2 つ。stringify → parse の時間は、古事記の全巻で 2cd9370 比 0.94〜1.18 (5 回の中央値、2 回の計測)。
- PR #73 (bfdb002): 描画と `READING_OVERLAP`。`vitest bench` で、AIR・html・canvas の時間は c34e924 比 0.96〜1.69 倍 (各 3 回の平均、2 回の計測)。最大は KanbunKundoku の 1.55〜1.69 倍で、増えた分の大半は AIR の組み立て。

## 受け入れた限界

- 描画の上限 (1,024、8、56) は、設計の段階では決めておらず、描画の実装で決めた。
- canvas で、傍線の中の範囲の読みが長いと傍線の外にはみ出す。
- 同じ字の 2 つ目以降の傍点は描かない。傍点は字の横の 1 つの置き場で、style が同じなら見た目は変わらない。
- AIR の組み立ては、KanbunKundoku で c34e924 の約 1.6 倍遅い。原因は調べていない。
- 古い parser は `<skam:t>`、空要素の対、`skam:ext` / `skam:custom` を黙って落とす。

## 経緯の記録

- VRT の基準画像は c84125c から、縦書きの基準線の補正 (`calibrateGridBaselineInPage`) を呼ばないページで撮られ、範囲の読みの後ろの字がずれていた。playground は補正を呼んでいて正しかった。利用者の指摘で分かり、PR #73 でテストのページが補正を呼ぶようにし、基準画像 10 枚を撮り直した。
- 描画の実装の途中で、送り仮名の範囲を字の slot に置いたところ、範囲の中で改行が入るようになった。字の slot に `joinedWithNext` を足し、validator の不可分単位と同じ規則で改行の位置を決めて直した。
- 同じ字の後ろの ref 2 つ、句読点 2 つで後の 1 つが消える退行が出た。slot を配列 (`refLabels`、`kutotenValues`) にして直した。
